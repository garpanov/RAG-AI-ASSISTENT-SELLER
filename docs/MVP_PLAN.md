# План MVP платформи AI-підтримки

## Резюме

Створити асинхронний FastAPI backend для окремого deployment кожної компанії. Система відповідатиме на типові запити через RAG, отримуватиме інформацію про замовлення через адаптер і переводитиме діалог до менеджера, коли відповідь потребує людського рішення.

## Ключові зміни

- Перевести проєкт на Python 3.14 та структуру Router → Service → Repository → PostgreSQL.
- Додати конфігурацію через environment variables, async SQLAlchemy 2, psycopg, pgvector та Alembic; прибрати створення таблиць із runtime-коду.
- Реалізувати сутності:
  - `Conversation` зі станами `bot`, `waiting_manager`, `manager`, `closed`.
  - `Message` з автором `customer`, `assistant` або `manager`.
  - `KnowledgeDocument` і `KnowledgeChunk` з embedding.
  - `Handoff` із причиною, статусом і призначеним менеджером.
  - `ApiKey` із хешованим секретом і роллю `client`, `manager` або `admin`.
- Реалізувати RAG-конвеєр: нормалізація тексту, поділ документа на фрагменти, embeddings, vector search, формування контексту та генерація відповіді з посиланнями на джерела.
- Додати інтерфейси `LLMProvider`, `EmbeddingProvider` та `OrderProvider`. Конкретні зовнішні інтеграції не входять у MVP; для локального запуску й тестів використовувати детерміновані reference/fake-адаптери.
- Логіка передачі менеджеру має враховувати явне прохання клієнта, низьку впевненість RAG, відсутність релевантних джерел, помилку інтеграції замовлень і запити, позначені моделлю як такі, що потребують людського рішення.
- Після handoff бот не генерує нових відповідей, доки менеджер не закриє діалог або не поверне його боту.
- Додати структуровані логи, correlation ID, health/readiness endpoints і безпечне логування без текстів повідомлень, ключів та персональних даних.

## Публічні інтерфейси

- `POST /v1/conversations` — створити діалог.
- `POST /v1/conversations/{id}/messages` — надіслати повідомлення й отримати відповідь або статус передачі.
- `GET /v1/conversations/{id}/messages` — отримати історію з пагінацією.
- `POST /v1/conversations/{id}/close` — закрити діалог.
- `GET /v1/manager/conversations` — черга діалогів, що потребують менеджера.
- `POST /v1/manager/conversations/{id}/claim` — призначити діалог поточному менеджеру.
- `POST /v1/manager/conversations/{id}/messages` — надіслати відповідь менеджера.
- `POST /v1/manager/conversations/{id}/return-to-bot` — повернути діалог боту.
- `POST/GET/PATCH/DELETE /v1/admin/knowledge/documents` — керування текстовою базою знань; створення та оновлення автоматично переіндексовують chunks.
- `POST /v1/orders/query` — нормалізований доступ до `OrderProvider`.
- `GET /health` і `GET /ready` — стан застосунку та залежностей.
- JSON-схеми, помилки й OpenAPI мають бути типізовані через Pydantic; client key передається в `X-API-Key`, manager/admin key додатково перевіряється за роллю.

## Етапи реалізації

1. Створити package-структуру застосунку, settings, async database session, dependency injection і базовий FastAPI entrypoint.
2. Описати SQLAlchemy-моделі, repositories та початкову Alembic-міграцію з розширенням `vector` й індексами.
3. Реалізувати API-key авторизацію, ролі та CRUD бази знань.
4. Реалізувати індексацію документів і vector retrieval із конфігурованими розміром chunks, overlap, кількістю результатів і порогом релевантності.
5. Реалізувати orchestration сервіс діалогу, провайдерні інтерфейси, правила handoff і життєвий цикл менеджерського чату.
6. Оновити Docker Compose для застосунку та PostgreSQL/pgvector, додати `.env.example`, команди міграцій і документацію локального запуску.
7. Налаштувати Ruff, mypy і pytest відповідно до Python 3.14.

## Перевірка та критерії приймання

- Unit-тести сервісів: успішна RAG-відповідь, відсутність контексту, явний запит менеджера, проблемне замовлення, помилка провайдера та заборона відповіді бота після handoff.
- Repository-тести проти PostgreSQL/pgvector: CRUD, vector search, транзакції, пагінація та конкурентне призначення менеджера.
- API-тести: ролі й ключі, статус-коди, валідація, ізоляція admin/manager endpoint-ів і повний сценарій діалогу.
- Міграційний тест на чистій базі та перевірка повторного запуску застосунку без `create_all`.
- Повний сценарій: документ індексується, типове питання отримує grounded-відповідь, специфічне питання потрапляє в чергу, менеджер забирає діалог і відповідає.
- Перед завершенням виконати `ruff check .`, `mypy .` і `pytest`.

## Припущення та межі MVP

- Кожна компанія має окремі deployment, базу, секрети та конфігурацію; `tenant_id` не потрібен.
- MVP містить лише backend API, без клієнтського віджета, адмінпанелі та UI менеджера.
- Обмін повідомленнями виконується через REST із polling; WebSocket/SSE можна додати окремо без зміни доменної моделі.
- База знань приймає текст; PDF/DOCX, web crawling і фонові конектори не входять у MVP.
- Зовнішня CRM/ERP, конкретний LLM і embedding-сервіс підключаються адаптерами в наступних інтеграціях.
- Історія діалогів зберігається безстроково в MVP; retention, видалення персональних даних і аналітика потребуватимуть окремої політики.
